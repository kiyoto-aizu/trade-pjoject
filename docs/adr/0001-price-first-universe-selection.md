# ADR-0001: 銘柄選定を「価格上限先行型ユニバース」に変更する

## ステータス

提案中(実装前) / 2026-09-19

## 背景・課題

現在の①スクリーニング(`ScreeningUseCase`)は、kabu STATION APIの`/ranking`エンドポイント
(値上がり率ランキング・売買代金ランキング、それぞれ市場全体の上位50件)を取得し、両者を
統合(`merge_ranking_candidates`)した後に、事後的に価格上限フィルタ(`filter_candidates_by_price`)
と規制除外(`exclude_by_regulation`)をかけて候補を絞り込んでいる。

この構造には2つの問題がある。

1. **候補の母数が想定より大幅に少ない**
   当初は30〜50銘柄程度を候補にしたい想定だったが、実際には「TOP50∪TOP50」という
   数十〜100件規模の母集団に対して価格上限フィルタと規制除外を事後適用するため、
   最終的な候補が10銘柄程度まで縮んでしまっている。

2. **「値上がり銘柄を狙う」ことと「予算内の株価に収める」ことが構造的に対立する**
   `analyze_filter_entry_alignment.py`による診断(2026-09-19、13営業日分・114件の
   日付×銘柄の組を対象)で以下が判明した。

   - エントリー条件(価格モメンタム+RSI)自体が成立していた割合: **72.8%(83件)**
   - そのうち実際に予算内(1銘柄あたり予算3万円、100株単位→株価上限約270〜300円)で
     購入可能だったのは **21.1%(24件)** のみ
   - 残り **51.8%(59件)** は、エントリー条件は満たしていたが株価が予算上限を超えており
     購入不可だった
   - 24件 ÷ 13日 ≈ 1.85件/日 であり、これは実運用で観測されている
     「1〜2件/日」という買付件数の少なさとほぼ一致する

   原因は、①スクリーニングの価格上限フィルタが**前営業日の終値時点**で判定される一方、
   候補選定自体が値上がり率ランキング(`RankingType.PRICE_GAIN`)を積極的に取り込んでおり、
   「前日時点では予算内だったが、値上がりが続いたことで当日には予算上限を超えてしまう」
   銘柄が大半を占めるためと考えられる。「安い銘柄」と「勢いよく上がっている銘柄」が
   この母集団では両立しにくい、という構造的な自己矛盾が数字として裏付けられた。

   なお、`OPERATING_CAPITAL`単体を引き上げる対応は効果がないことも確認済み。
   `budget_per_position = min(OPERATING_CAPITAL / TARGET_POSITIONS, MAX_ORDER_AMOUNT_PER_TRADE)`
   という計算式上、現状は`MAX_ORDER_AMOUNT_PER_TRADE`(3万円)側が制約になっており、
   `OPERATING_CAPITAL`だけを増やしても価格上限は変わらない。

## 決定

銘柄選定の順序を「ランキング取得 → 事後的に価格で絞る」から、
**「先に価格で絞ったユニバースを作り、その中でランキングする」**方式に変更する。

新しいパイプライン:

1. 上場銘柄マスタ(新規に用意。週次更新で十分と判断)から全銘柄を取得する
2. 価格上限(`get_screening_price_cap()`、既存ロジックをそのまま流用)以下の銘柄に絞る
3. 規制銘柄を除外する(既存の`exclude_by_regulation`をそのまま流用。
   以後の出来高・値上がり率計算で無駄なAPIコールを発生させないため、この段階で行う)
4. 残った銘柄について、出来高急増率・値上がり率を自前で計算する
   (`HistoricalRankingRepository`がバックテスト用に持っている手法を、本番用に応用する)
5. 出来高急増率と値上がり率を統合してランキングを作る。ただしADR-0002とは別に、
   値上がり率側の重みを下げる(等重みの単純合算をやめ、重み付き合算にする)。
   具体的な重み係数は、値上がり率と事後の予算超過率との相関を見て決める
6. 候補数が多い場合は上位30〜50件に絞る(`limit_candidates`と同様の考え方)

kabu STATIONの`/ranking`APIには価格レンジで絞り込むパラメータが存在しないため
(`references/kabu_STATION_API.yaml`で確認済み)、この変更はAPIの差し替えではなく、
**ランキング機能そのものを自前実装に置き換える**アーキテクチャ変更になる。

上場銘柄マスタの更新頻度は週次で十分と判断した。東証全体のIPO・上場廃止は
月に数件〜十数件程度であり、数日〜1週間のずれによる実害は小さい
(新規上場が数日遅れて候補に入る、上場廃止銘柄がしばらく残っても板情報が
取れずスキップされるだけ)。

APIコール数は増加する。上場銘柄マスタ全体(東証全体で3,900〜4,000銘柄前後)に対して
日次で終値・出来高の取得が必要になり、既存の`API_REQUEST_INTERVAL_SECONDS=0.12`を
適用すると概算8分程度かかる。ただし①スクリーニングは大引け後に実行するバッチ処理であり、
処理時間の制約は緩いため許容する。

## 期待する効果

- 「エントリー条件成立・予算内で購入可能」の割合(現状21.1%)を、
  「エントリー条件成立」の割合(72.8%)に近づける
- 結果として実際の買付件数を、現状の1〜2件/日から`TARGET_POSITIONS`(3件/日)に近づける
- 低予算フェーズでの決済済み取引の蓄積速度を上げ、投資額を引き上げる判断材料を早く揃える

**期待していないこと**(誤解防止のため明記): 勝率や損益そのものの改善を狙うものではない。
あくまで試行回数を増やすための施策であり、低位株特有の値動きの荒さが緩和されるわけでもない。

## 検討した代替案

- **方向2: ミーンリバージョンの再導入(選定ロジックごと作り直し)**
  却下。2026-09-11のレビュー(`docs/strategy-review-2026-09-11.md`)で、
  「選定は上昇・注目銘柄を拾うのに、シグナルは下落・売られすぎ銘柄を買う」という
  向きの不一致により買いシグナルが恒常的に0件になる問題が確認され、
  トレンドフォロー方式に転換した経緯がある。エントリー条件だけをミーンリバージョンに
  戻すと、この問題が再発する。選定ロジックも含めて全面的に作り直す必要があり、
  影響範囲が最も大きいため、今回は見送る。

- **方向4: 固定の低位株ウォッチリスト運用への切り替え**
  却下。「市場全体から日々動的に選び直す」という現在の設計思想自体を変えることになり、
  影響範囲が大きい。

- **`OPERATING_CAPITAL`のみの引き上げ**
  却下。上記の通り、`MAX_ORDER_AMOUNT_PER_TRADE`との`min()`により効果がないことを確認済み。

- **過去データによる厳密な重み替えシミュレーション**
  見送り。`HistoricalRankingRepository`が依存する`YahooFinanceClient.get_daily_market_data`は
  銘柄×日付ごとに個別API呼び出しが必要で日をまたいだキャッシュもないため、
  市場全体×複数日のランキング再構築には数万回規模のAPI呼び出しが必要になり非現実的。
  また`data/filtering/*.json`には最終候補の銘柄名のみが記録されており、
  各銘柄のランキング順位そのものは残っていないため、過去データからの厳密な再現も困難。
  代わりに、値上がり率と事後の予算超過率との相関を見る軽量な代理分析で
  重み係数の当たりをつける方針とする。

## 影響・トレードオフ

- 上場銘柄マスタを新規に用意し、週次更新するバッチ処理が必要になる
- ①スクリーニングのAPIコール数が大幅に増加する(既存: 上位50件×2 → 変更後: 全銘柄規模)
- ①スクリーニングの実装がkabu STATIONの`/ranking`APIへの依存から、
  自前のランキング計算ロジックへの依存に変わる
- 出来高急増率・値上がり率の計算方法(自前実装)が、②フィルタリング側の計算方法と
  重複・類似する可能性があり、実装時に共通化を検討する余地がある
