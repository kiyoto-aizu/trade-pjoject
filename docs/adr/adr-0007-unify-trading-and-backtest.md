# ADR-0007(案): バックテストを本番`TradingUseCase.run()`のオフライン実行として統合する

## ステータス

承認 / 段階的実装へ移行（2026-09-25、確認事項1〜5への回答を反映。詳細は
「全体ロードマップ」を参照。各フェーズの実装プロンプトは着手時に個別作成する）

## 背景・課題

`trading_usecase.py`(本番)と`backtest_usecase.py`(バックテスト)は、domain層の
純粋関数(`TradeSignal.evaluate`、`is_atr_stop_loss_triggered`等)こそ共有しているが、
「いつ・何を引数にしてそれらを呼ぶか」を組み立てるapplication層のオーケストレーション
コードは完全に別実装になっている。

この構造により、ADR-0002(トレーリングストップ利確)や過去のIssue 3(予算配分ロジック)の
ように「状態を持つ仕様変更」が発生するたびに、本番側だけ直してバックテスト側への
反映が漏れる、という同型の不具合が繰り返し発生している。根本原因は「2つの独立した
実装を人力で同期し続ける」という構造そのものにあるため、対症療法ではなく
`TradingUseCase`のメインループ(`run()`)自体をバックテストでも再利用する形に統合し、
実装の二重管理をなくすことを目指す。

## 現状把握（統合の足がかりになる既存設計）

`TradingUseCase`は現時点で以下の依存性注入ポイントをすでに持っており、統合の
土台としては悪くない状態にある。

- `market_data_client` / `board_client` / `wallet_client` / `positions_client` /
  `order_sender` / `notifier` / `filter_decision_repository` — いずれもコンストラクタで
  差し替え可能（現状はテスト用途のオプション引数）
- `run(top_symbols_path, now_provider, sleep, preflight_market_data)` —
  時刻取得関数とスリープ関数がすでに注入可能（テストで実時間を待たずに
  ループを検証する用途で使われている）
- `run()`は「当日のフィルタ結果を読み込み、大引けまでループし、大引けで
  `_liquidate_all_positions()`する」という**1営業日単位**の設計になっている

この2点から、「過去データを返す疑似クライアント一式」+「進行する`now_provider`」+
「即時リターンする`sleep`」を注入した`TradingUseCase`を、対象期間の営業日ごとに
1回ずつ`run()`する、という統合方式が現実的な選択肢として見えている。

## 決定（提案）

`simulate_backtest` / `simulate_timeseries_backtest`という独立した2つのシミュレーション
関数を廃止し、`TradingUseCase.run()`を「過去データ再生モードで実行する」ことで
バックテストを行う方式に置き換える。

- 疑似`MarketDataClient`・`BoardClient`・`WalletClient`・`PositionsClient`・
  `OrderSender`を新設し、ヒストリカルデータ(日足/分足)を本番と同じインターフェースで
  返す/受け取るようにする
- `FilteringResultRepository`にも過去日付のフィルタ結果を返す疑似実装を用意し、
  「当日のフィルタ結果」読み込み部分をそのまま流用する
- 対象期間の営業日ごとに、その日の疑似クライアント一式を差し替えて`run()`を
  1回ずつ呼び出す（`_holding_high_prices`等の日次状態は`run()`冒頭で
  クリアされる設計のため、日をまたぐ状態リセットも自然に踏襲される）
- `now_provider`は疑似時計（分足データのタイムスタンプを順に返す/日足のみの場合は
  寄り〜引けの代表時刻を返す）とし、`sleep`は即時リターンする関数を注入する

## 検討した代替案

- **現状維持＋パリティテストで検知**: ズレの早期発見はできるが、発生自体は防げず
  実装漏れは今後も起き続ける。案4を「あるべき姿」とするなら中間策にしかならない
- **状態管理だけを共有クラスに切り出す(案1)**: 今回のトレーリングストップの件は
  解決するが、「予算配分」「キルスイッチ」等、状態を伴う仕様変更が今後別の箇所で
  起きるたびに同じ切り出し作業が要る。都度対応であり、根本解決ではないと判断し、
  今回は不採用（ただし後述のとおり、統合の移行過程で結果的に近い形になる可能性はある）

## リスク・懸念事項

1. **パフォーマンス**: `run()`は「1銘柄ずつAPI呼び出し→判定→スリープ」という
   実運用向けの設計であり、大量の過去データ(例: 数ヶ月×分足)を高速に流すには
   `sleep`をゼロにするだけでは不十分な可能性がある。ループ内のログ出力量・
   ファイルI/O(`_save_order_history`など毎回の永続化処理)がボトルネックになりうる
2. **疑似クライアントの忠実度が新しい乖離源になる**: 「2つの実装を同期し続ける
   リスク」を「本番APIのレスポンス形式を疑似クライアントで正確に再現し続ける
   リスク」に置き換えるだけ、という側面がある。特にkabuStation APIのレスポンス
   フォーマット変更に本番側だけ追従し、疑似クライアント側の更新が漏れる、という
   形で同種の問題が再発する可能性は残る
3. **既存バックテスト固有機能の移植コスト**: `simulate_timeseries_backtest`が
   持つ複数銘柄同時進行・分足/日足切り替え(`indicator_source`)・
   マーケットレジーム系列の事前計算・手数料/スリッページ/約定遅延モデル
   (`_calculate_execution_price`)などは、`run()`側には現状存在しない機能であり、
   移植または疑似クライアント側での再現が必要
4. **下流ツールへの影響範囲**: `run_weekly_analysis.py`・`run_monthly_analysis.py`・
   diary生成・`analyze_filter_entry_alignment.py`等、`latest_timeseries.json`や
   `simulate_backtest`系の出力フォーマットに依存する分析ツール群がある。
   出力フォーマットの互換性を保つか、これらも合わせて改修するかの判断が必要
5. **テスト資産への影響**: `tests/test_backtest.py`をはじめ、現行の2エンジンを
   前提にしたテストが多数存在する。統合後はこれらの大部分を書き直すことになる
6. **移行期間中の並存コスト**: 一気に置き換えるのはリスクが高いため、移行期間中は
   新旧2つの経路が並存する可能性が高く、その間は「本来なくしたかった二重管理」が
   一時的に増える形になる

## 確認事項への回答(2026-09-25)

1. **移行方針**: 新エンジンを既存エンジンと並行稼働させ、同一データでの結果を
   突き合わせてから旧エンジン(`simulate_backtest`/`simulate_timeseries_backtest`)を
   廃止する。両エンジンの結果差異が「新エンジンの不具合」か「旧エンジンで
   未実装だった機能」かを見極めた上で廃止判断する
2. **性能要件**: 3ヶ月×10銘柄・分足ありを基準に設計する。概算では
   63営業日×10銘柄×約390分足 ≈ 24.6万ティックの評価が必要になる規模。
   domain層の判定自体(RSI/ATR計算等)は純粋計算で軽量なため、ボトルネックは
   むしろ毎ティックのログ出力・注文履歴の永続化(`_save_order_history`)等の
   I/O側になる可能性が高い。フェーズ2(下記)の検証時に実測し、必要なら
   バックテストモード限定でI/O頻度を落とす対応(バッチ書き込み化等)を入れる
3. **既存分析ツール群との互換性**: 互換性維持を優先せず、この機会に
   `run_weekly_analysis.py`・`run_monthly_analysis.py`・diary生成・
   `analyze_filter_entry_alignment.py`等の入出力も合わせて見直す。
   ただし影響範囲が広いため、新エンジンのコア(疑似実行そのもの)が
   安定してから着手する(フェーズ5)
4. **着手時期**: 3ヶ月データ蓄積フェーズの「新規機能開発を抑える」方針とは
   別枠の「基盤整備」として、並行して進める
5. **段階分割**: 大きく分割して進める。全体像は次節「全体ロードマップ」の
   とおりで、各フェーズ着手時に改めて実装プロンプト(またはフェーズ内で
   設計判断が要る場合は個別ADR)を作成する

現在地: フェーズ0(準備)として、ADR-0002(利確ロジック)の`simulate_timeseries_backtest`への
反映漏れ修正を別タスクで先行実施済み(実装プロンプト出力済み・実行はこれから)。
この統合(フェーズ1〜6)は、その修正が本番/バックテストの一時的な整合性を保つための
ものであり、統合完了後は`simulate_timeseries_backtest`自体が廃止される見込みのため、
今回の修正が無駄にならない範囲(=フェーズ4の突合検証時の比較対象として有用)である
ことを踏まえて先行させている。

## 影響・トレードオフ（各フェーズ実施時に更新）

### フェーズ1着手時の追記(2026-09-25): リスク②の再評価

リポジトリを精査した結果、`TradingUseCase`の依存クライアントは正式なProtocol/ABCではなく
ダックタイピング(メソッド名一致のみで動作)で、かつ`order_sender`が
`get_wallet_cash`/`get_positions`等を持っていれば`wallet_client`/`positions_client`が
未注入でも自動的にフォールバックする設計になっていた。さらに、ペーパートレードで
実際に使われている`PaperOrderClient`(`src/infrastructure/paper/paper_order_executor.py`)が
現金・保有株・平均取得単価・手数料・スリッページ・実現損益計算を一手に担っており、
これは**バックテストの注文約定シミュレーションが本来必要とする処理そのもの**である。

そのため`order_sender`は新規実装不要で、`PaperOrderClient(state_path=None)`を
そのまま流用できる。これによりリスク②(疑似クライアントの忠実度)のうち
「注文約定・資金管理ロジックの二重実装」という最大の懸念が実質的に解消された
(本番/ペーパー/バックテストの3者が同一の約定シミュレーションコードを共有する形になる)。
新規実装が必要なのは「価格の供給元」(板情報・日足データ)と「日付送りのオーケストレーション」
のみに絞り込めたため、当初想定より軽量に進められる見込み。詳細はフェーズ1設計書を参照。
